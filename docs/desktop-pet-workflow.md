## 工作方式

每个小功能都按同一流程推进：

`定义验收条件 → 从 main 创建功能分支 → 编写功能 → 运行验证 → 提交 → 合并回 main → 验证主干 → 开始下一个分支`

- `main` 保存已经验证、能够运行的集成版本。
- 每个分支解决一个明确的小目标，完成后尽早合并；后续分支从最新的 `main` 创建。
- Git 分支用于组织版本；Python 模块用于组织代码。模块之间的调用、事件和状态连接，需要在开发时实现并验证。
- Git 的 `main` 分支与文件 `main.py` 是不同概念：前者是版本线，后者可以作为程序入口。
- 普通开发不必额外设置 `develop` 分支。当前单人项目先用 `main + 功能分支` 即可。

## 第 0 步：保存可运行基线

目标：把现在成功的版本保存成可以回退的起点。

- [ ] 选择固定解释器，记录 SDK 和配套运行时版本。
- [ ] 再运行一次当前程序，确认收到回复且结束原因是 `completed`。
- [ ] 建立根目录 `.gitignore`。
- [ ] 确认提交只包含代码、依赖声明、说明文档和必要素材。
- [ ] 检查暂存内容，再完成第一次提交。
- [ ] 可选：为这次提交标记 `v0.1.0-cli`。

建议的 `.gitignore` 起点：

```gitignore

__pycache__/
*.py[cod]
.env
.env.*
```

## 第 3 步：桌宠与 Harness 连起来

为便于排错，这一阶段拆成两个分支，依次完成并合并。

### 3A：封装调用代码

分支：`refactor/harness-client`

- [ ] 把创建 Harness、发送消息和获取结果封装到独立模块。
- [ ] 参数从配置传入，避免把界面操作写进底层调用模块。
- [ ] 提供清晰的成功、失败结果，保留可用于排错的信息。
- [ ] 终端版本改为调用这个模块，并保持一次对话成功。

验收：同一套底层调用既能被终端程序使用，也能供后面的界面调用。

### 3B：接入聊天窗口

分支：`feat/pet-chat`

- [ ] 点击桌宠可以打开输入和回复界面。
- [ ] 输入文字后交给 Harness，返回内容显示在界面上。
- [ ] 请求等待期间仍能拖动窗口和进行基本操作。
- [ ] 显示等待、成功和错误状态；错误不会让整个界面退出。
- [ ] 如果支持连续聊天，确认后续消息使用同一会话，并用上一轮信息验证上下文。
- [ ] 退出程序时正确关闭后台任务和 Harness 运行时。

验收：从界面发出问题，收到回复，过程中窗口保持响应。

每个分支完成后都合并回 `main`，不要等整个聊天模块写完才第一次集成。

## Git 操作模板

前提：第 0 步已经产生第一次提交；开始新分支前，先处理好未提交修改。

```powershell
git switch main
git status
git switch -c feat/pet-window
```

编写代码并通过验收后，在 PyCharm 提交界面选择本次功能的文件并提交。提交说明示例：`feat: add draggable pet window`。提交前确认没有遗漏新文件，也没有混入运行数据。

完成提交后：

```powershell
git switch main
git merge --no-ff feat/pet-window
```

合并后运行主程序，检查新功能及原来的功能。确认正常且分支已经合并，才考虑删除功能分支：

```powershell
git branch -d feat/pet-window
```

下一步再从最新的 `main` 创建新分支。若出现冲突，检查并理解冲突两侧的改动，解决后重新运行验收；不要仅为消除提示而随意保留一侧。

Git 提交保存本地版本，推送到远程仓库是另一项操作。是否设置远程以及何时推送，由你决定；本工作流不要求立即推送。
